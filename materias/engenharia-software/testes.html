Destaques Cesgranrio — Testes

  • Verificação ("construímos certo?") vs Validação ("construímos o certo?") — inversão clássica
  • Ordem dos níveis: Unitário → Integração → Sistema → Aceitação
  • Caixa-branca = estrutura interna do código; Caixa-preta = especificação (sem ver o código)
  • TDD: escreve o teste ANTES do código; ciclo Red-Green-Refactor
  • SAST = análise estática (sem executar); DAST = análise dinâmica (em execução)
  • Teste de regressão: garante que novas mudanças não quebraram o que funcionava

Verificação & Validação

⭐ A Distinção Fundamental (Boehm)
Verificação: "Estamos construindo o produto CORRETAMENTE?" — conformidade com a especificação técnica. Atividade INTERNA da equipe de desenvolvimento.

Validação: "Estamos construindo o produto CERTO?" — o sistema atende às necessidades REAIS do usuário/cliente. Atividade com o CLIENTE/usuário.
AspectoVerificaçãoValidação
Pergunta"Construímos corretamente?""Construímos o certo?"
ReferênciaEspecificação de requisitosNecessidades reais do usuário
Quem realizaEquipe técnica (desenvolvedores, QA)Cliente, usuários finais
QuandoDurante todo o desenvolvimentoFinal ou incremental (UAT)
TécnicasRevisão de código, testes unitários, inspeçõesTeste de aceitação (UAT), demonstrações
ObjetivoConformidade com a especificaçãoAdequação ao uso
⚠️ Como memorizar sem errar
Verificação → Verificar a spec (especificação = interno, técnico)
Validação → Validar com o cliente (usuário = externo, negócio)

Dica alternativa: Validação tem "usuário" na resposta correta. Se a alternativa mencionar "cliente" ou "usuário final", provavelmente é Validação.

Níveis de Teste

1

Teste Unitário (Unit Testing)

O que testa: Menor unidade testável do código — função, método, classe — em isolamento.
Responsável: Desenvolvedor (escrito junto com o código).
Isolamento: Usa mocks/stubs para simular dependências externas.
Ferramentas: JUnit (Java), pytest (Python), Jest (JavaScript), NUnit (.NET).
Velocidade: Muito rápido — centenas por segundo.

2

Teste de Integração

O que testa: Interação entre módulos/componentes/serviços — interfaces e contratos.
Responsável: Desenvolvedor ou QA.
Detecta: Problemas de comunicação entre unidades (ex: formato de dados incorreto entre serviços).
Abordagens: Big Bang (tudo de uma vez), Top-Down, Bottom-Up.

3

Teste de Sistema

O que testa: Sistema completo e integrado contra os requisitos especificados.
Responsável: Time de QA (independente do desenvolvimento).
Inclui: Testes funcionais + não-funcionais (performance, segurança, usabilidade).
Ambiente: Staging — réplica de produção.

4

Teste de Aceitação (UAT)

O que testa: Se o sistema atende aos critérios de aceitação de negócio.
Responsável: Cliente / Usuários finais.
Última fase antes do deploy em produção.
Tipos: Alpha (ambiente controlado do fornecedor), Beta (usuários reais em produção limitada).

Outros Tipos Importantes

TipoObjetivo
RegressãoGarante que novas mudanças não quebraram funcionalidades existentes. Automatizado no CI/CD.
Fumaça (Smoke Test)Teste rápido das funcionalidades críticas após um build — "o sistema sobe?"
Performance / CargaVerifica comportamento sob carga: tempo de resposta, throughput, limites.
StressLeva o sistema além do limite para identificar ponto de falha.
UsabilidadeAvalia facilidade de uso com usuários reais observados.
Segurança (Pentest)Simula ataques para identificar vulnerabilidades.

Técnicas de Teste

Caixa-Branca vs Caixa-Preta vs Caixa-Cinza

TécnicaConhece o código?Base dos testesQuem usa
Caixa-Branca
(White-box / Estrutural)		 ✅ Sim — total Estrutura interna: caminhos, condições, instruções, fluxos Desenvolvedor
Caixa-Preta
(Black-box / Funcional)		 ❌ Não Especificação/requisitos — apenas entradas e saídas esperadas QA, usuário
Caixa-Cinza
(Grey-box)		 ⚠️ Parcial Conhecimento parcial da implementação para guiar os testes QA sênior

Técnicas de Caixa-Preta

📊
Partição de Equivalência
Divide entradas em classes equivalentes. Um teste por classe. Ex: salário válido (0-50k), inválido negativo, inválido acima do limite.
🎯
Análise de Valor Limite
Testa exatamente nos limites (boundary values). Ex: para campo 1-100, testa: 0, 1, 2, 99, 100, 101.
📋
Tabela de Decisão
Mapeia combinações de condições e ações. Garante cobertura de todas as regras de negócio.
🔄
Transição de Estado
Testa mudanças de estado do sistema. Ex: pedido (rascunho → enviado → aprovado → pago).

SAST, DAST e IAST — Testes de Segurança

TécnicaQuandoComoVantagem principal
SAST
Static AST		 Durante desenvolvimento (CI) Analisa código-fonte sem executar — busca padrões de vulnerabilidade Detecta cedo, sem executar, aponta linha do código
DAST
Dynamic AST		 Após deploy (staging) Testa a aplicação em execução, simulando ataques externos (black-box) Detecta vulnerabilidades reais de runtime, sem acesso ao código
IAST
Interactive AST		 Durante testes funcionais Agente instrumentado dentro da aplicação em execução monitora em tempo real Precisão de SAST + realismo de DAST, baixo falso-positivo

TDD e BDD

TDD — Test-Driven Development

⭐ TDD — Desenvolvimento Guiado por Testes
Escreva o teste ANTES de escrever o código de produção. Ciclo: Red → Green → Refactor.
🔴

Red — Escreva um teste que falha

Escreva um teste para a funcionalidade que ainda não existe. O teste deve falhar (vermelho) — confirma que o teste é válido.

🟢

Green — Faça o teste passar

Escreva o MÍNIMO de código necessário para fazer o teste passar (verde). Não otimize ainda.

🔵

Refactor — Melhore o código

Refatore o código mantendo todos os testes passando. Elimine duplicações, melhore legibilidade e design.

💡 Benefícios do TDD
Alta cobertura de testes automática, design emergente (código mais simples e testável), confiança para refatorar, documentação viva (testes descrevem comportamento esperado). Custo: maior tempo inicial de desenvolvimento.

BDD — Behavior-Driven Development

Extensão do TDD que usa linguagem natural (Gherkin) para descrever comportamentos do sistema, facilitando colaboração entre desenvolvedores, QA e stakeholders de negócio.

Gherkin — BDD
Feature: Aprovação de Orçamento
  Como gerente financeiro
  Quero aprovar orçamentos pelo sistema
  Para que o processo seja auditável e rápido

  Scenario: Aprovar orçamento dentro do limite
    Given que existe um orçamento de R$ 50.000 pendente
    And meu limite de aprovação é R$ 100.000
    When eu aprovar o orçamento
    Then o status deve mudar para "Aprovado"
    And o solicitante deve receber notificação por email

  Scenario: Rejeitar orçamento acima do limite
    Given que existe um orçamento de R$ 150.000 pendente
    And meu limite de aprovação é R$ 100.000
    When eu tentar aprovar o orçamento
    Then o sistema deve exibir mensagem de erro
    And encaminhar para aprovação do nível superior

Qualidade de Software — ISO 25010

O modelo de qualidade ISO 25010 (successor da ISO 9126) define características de qualidade para produtos de software:

✅
Adequação Funcional
O software faz o que deve fazer? Completude, correção e pertinência das funções.
⚡
Eficiência de Performance
Comportamento temporal, uso de recursos e capacidade.
🔧
Manutenibilidade
Modularidade, reusabilidade, analisabilidade, modificabilidade, testabilidade.
🛡️
Segurança
Confidencialidade, integridade, não-repúdio, responsabilização, autenticidade.
✅
Confiabilidade
Maturidade, disponibilidade, tolerância a falhas, recuperabilidade.
😊
Usabilidade
Reconhecibilidade, aprendizabilidade, operabilidade, proteção contra erros.
