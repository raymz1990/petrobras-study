Requisitos de Software

Requisitos descrevem o que o sistema deve fazer (funcionais) e as restrições sob as quais deve operar (não-funcionais). O levantamento inadequado é a principal causa de falha em projetos de software.

Tipos de Requisitos

TipoDefiniçãoExemplos
Funcionais (RF) O que o sistema deve FAZER — funcionalidades, comportamentos, regras de negócio "O sistema deve permitir login com CPF e senha", "Gerar relatório de produção diário"
Não-Funcionais (RNF) Como o sistema deve SER — qualidade, restrições, atributos Performance, segurança, disponibilidade, usabilidade, escalabilidade
Negócio Objetivos de alto nível da organização que motivam o sistema "Reduzir tempo de emissão de NF em 30%"
Usuário O que os usuários precisam fazer com o sistema Histórias de usuário, casos de uso
⚠️ Pegadinha — RF vs RNF
"O sistema deve responder em menos de 2 segundos" → RNF (performance).
"O sistema deve calcular o imposto sobre o salário" → RF (funcionalidade).
"O sistema deve estar disponível 99,9% do tempo" → RNF (disponibilidade).
A banca frequentemente apresenta RNFs com verbo de ação para confundir.

Técnicas de Levantamento

🗣️
Entrevista
Conversa estruturada ou semiestruturada com stakeholders. Mais eficaz para requisitos complexos.
👥
Workshop/JAD
Joint Application Design — reunião colaborativa com usuários, desenvolvedores e analistas.
📋
Questionário
Para muitos usuários dispersos. Útil para confirmar requisitos já identificados.
🔍
Observação/Etnografia
Analista observa o usuário trabalhando. Revela requisitos implícitos não verbalizados.
📄
Análise de Documentos
Análise de formulários, relatórios e sistemas legados existentes.
🖥️
Prototipação
Criar protótipo para elicitar feedback. Muito eficaz quando usuários têm dificuldade de verbalizar necessidades.

Histórias de Usuário (User Stories)

📌 Formato padrão
Como [tipo de usuário], quero [objetivo/funcionalidade], para que [benefício/valor].

Exemplo: "Como analista de sistemas da Petrobras, quero visualizar o histórico de manutenção de equipamentos, para que possa identificar padrões de falha preventivamente."

Critérios de aceitação definem quando uma história está "pronta". As histórias devem seguir o critério INVEST: Independent, Negotiable, Valuable, Estimable, Small, Testable.

Ciclo de Vida de Sistemas

Modelos de Ciclo de Vida

💧 Cascata (Waterfall)

Sequencial e linear: Requisitos → Design → Implementação → Testes → Manutenção. Cada fase só começa quando a anterior é concluída.

✅ Melhor para: requisitos bem definidos, sistemas críticos, contratos governamentais.

❌ Problema: inflexível a mudanças; o cliente só vê o produto no final.

🌀 Espiral (Boehm)

Combina iteração com análise de riscos. Cada volta da espiral percorre: Planejamento → Análise de Riscos → Engenharia → Avaliação do Cliente.

✅ Melhor para: projetos grandes, alto risco, sistemas inovadores.

⭐ Destaque Cesgranrio: o modelo espiral foi proposto por Barry Boehm e tem foco central em gestão de riscos.

📦 Incremental

O sistema é construído e entregue em partes (incrementos). Cada incremento adiciona funcionalidade ao anterior.

✅ Melhor para: quando partes do sistema precisam ser entregues rapidamente. Permite feedback antecipado.

🔁 Iterativo

O sistema é desenvolvido em ciclos (iterações), refinando e melhorando a cada ciclo. Base dos métodos ágeis.

💡 Incremental vs Iterativo
Incremental = adiciona partes novas. Iterativo = refina o que já existe. Na prática, os métodos ágeis combinam os dois.
🏃 RUP — Rational Unified Process

Framework iterativo baseado em casos de uso e centrado na arquitetura. 4 fases: Concepção, Elaboração, Construção, Transição.

9 disciplinas (Requisitos, Análise e Design, Implementação, Testes...) executadas em diferentes intensidades em cada fase.

Usa UML como linguagem de modelagem padrão.

DevOps e CI/CD

ConceitoDefinição
DevOpsCultura que une Desenvolvimento e Operações para entregar software com mais velocidade e qualidade. Foco em automação e colaboração.
CI (Continuous Integration)Integrar código frequentemente (várias vezes ao dia) com execução automática de testes a cada integração.
CD (Continuous Delivery)Código sempre pronto para deploy em produção — o ato de publicar é manual (decisão humana).
CD (Continuous Deployment)Deploy automático em produção a cada integração que passa nos testes — sem intervenção humana.
PipelineConjunto automatizado de etapas: build → test → deploy. Garante qualidade contínua.

Modelagem — Estruturado e Orientado a Objetos

Paradigma Estruturado

📊
DFD
Diagrama de Fluxo de Dados. Mostra fluxo de dados entre processos, entidades e depósitos. Nivelado (contexto → N0 → N1...).
📋
DER
Diagrama Entidade-Relacionamento. Modelo conceitual do banco de dados — entidades, atributos e relacionamentos.
📐
Dicionário de Dados
Documenta cada elemento do DFD — fluxos, processos, depósitos e entidades externas.

UML — Unified Modeling Language

A UML é a linguagem padrão para modelagem orientada a objetos. Possui 14 tipos de diagramas divididos em estruturais e comportamentais.

DiagramaTipoO que modelaIncidência
Caso de UsoComportamentalInterações entre atores e o sistema. Fronteiras do sistema.Alta
ClasseEstruturalClasses, atributos, métodos e relacionamentos (herança, associação, dependência).Alta
SequênciaComportamentalTroca de mensagens entre objetos ao longo do tempo.Alta
AtividadeComportamentalFluxo de controle — similar a fluxograma, mas com swimlanes.Média
EstadoComportamentalCiclo de vida de um objeto — estados e transições.Média
ComponenteEstruturalOrganização e dependências entre componentes de software.Baixa

Conceitos de Orientação a Objetos

📦
Encapsulamento
Esconde detalhes internos. Dados acessados apenas via métodos públicos (interface). Reduz acoplamento.
🧬
Herança
Classe filha herda atributos e métodos da classe pai. Promove reutilização de código.
🎭
Polimorfismo
Mesmo método comportando-se diferente em classes diferentes. Sobrescrita (override) e sobrecarga (overload).
🔲
Abstração
Focar nos aspectos essenciais, ignorando detalhes irrelevantes. Classes abstratas e interfaces.

Verificação, Validação e Testes

⭐ Verificação vs. Validação — Definição Clássica (Boehm)
Verificação: "Estamos construindo o produto CORRETAMENTE?" — conformidade com a especificação. (Interno, equipe técnica)
Validação: "Estamos construindo o produto CERTO?" — o produto atende às necessidades do usuário. (Externo, com o cliente)
⚠️ Pegadinha Clássica da Cesgranrio
A banca inverte os conceitos. Decore assim: Verificação → está verificando a spec (interno). Validação → valida com o usuário (externo). Se der branco, lembre: validação tem "usuário/cliente" na resposta.

Níveis de Teste

1

Teste Unitário

Testa a menor unidade do código (função, método, classe) de forma isolada. Feito pelo desenvolvedor. Rápido e automatizável. Ferramentas: JUnit, PyTest, Jest.

2

Teste de Integração

Verifica a interação entre módulos/componentes. Detecta problemas de interface entre unidades. Feito pelo desenvolvedor ou QA.

3

Teste de Sistema

Testa o sistema completo contra os requisitos especificados. Feito pelo time de QA. Inclui testes funcionais e não-funcionais (performance, segurança).

4

Teste de Aceitação (UAT)

Feito pelo cliente/usuário final. Valida se o sistema atende aos critérios de aceitação de negócio. Última etapa antes do deploy em produção.
