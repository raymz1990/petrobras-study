Classificação de Requisitos

Hierarquia de Requisitos

1

Requisitos de Negócio

Objetivos estratégicos de alto nível que motivam o projeto. "Reduzir tempo de aprovação de orçamentos em 40%." Definidos pela alta gestão.

2

Requisitos de Usuário

O que os usuários precisam fazer com o sistema. Expressos em linguagem natural. "Como gerente, quero aprovar orçamentos pelo celular."

3

Requisitos de Sistema

Especificação detalhada do que o sistema deve fazer (funcionais) e como deve ser (não-funcionais). Base para design e desenvolvimento.

Funcionais vs Não-Funcionais

TipoDefineExemplos
Funcional (RF) O que o sistema deve FAZER — comportamento, funcionalidades, regras de negócio Login com CPF, gerar relatório PDF, calcular imposto, enviar e-mail de confirmação
Não-Funcional (RNF) Como o sistema deve SER — restrições de qualidade Resposta < 2s, disponibilidade 99,9%, suportar 1.000 usuários, criptografia AES-256

Categorias de RNF — ISO 25010

⚡
Performance
Tempo de resposta, throughput, uso de recursos. Ex: "Processar 500 transações/segundo."
🛡️
Segurança
Controle de acesso, criptografia, auditoria. Ex: "Autenticação por MFA para acesso externo."
✅
Confiabilidade
Disponibilidade, tolerância a falhas. Ex: "99,9% uptime = máx. 8,7h downtime/ano."
🔧
Manutenibilidade
Facilidade de modificar, corrigir e evoluir. Ex: "Cobertura de testes ≥ 80%."
📱
Portabilidade
Capacidade de operar em diferentes ambientes. Ex: "Funcionar em Chrome, Firefox e Safari."
😊
Usabilidade
Facilidade de uso. Ex: "Usuário completar tarefa em menos de 3 cliques."
⚠️ Pegadinha — RNF com verbo de ação
"O sistema deve criptografar senhas com AES-256" parece RF (tem verbo de ação) mas é RNF de segurança. O critério é: define uma funcionalidade de negócio (RF) ou uma restrição de qualidade/como deve ser implementado (RNF)?

Técnicas de Elicitação

TécnicaDescriçãoMelhor paraLimitação
Entrevista Conversa estruturada ou semiestruturada com stakeholders Requisitos complexos, contexto rico Demorado, depende de disponibilidade
JAD / Workshop Reunião colaborativa com usuários, analistas e devs Consenso rápido, requisitos conflitantes Requer facilitador experiente
Questionário Perguntas padronizadas enviadas a muitos usuários Grande número de usuários dispersos Respostas superficiais, sem diálogo
Observação / Etnografia Analista observa usuário trabalhando in loco Requisitos implícitos não verbalizados Usuário muda comportamento ao ser observado
Análise de Documentos Estuda documentos, formulários, sistemas existentes Sistemas legados, regras de negócio documentadas Documentação pode estar desatualizada
Prototipação Cria protótipo para elicitar feedback concreto Usuários com dificuldade de verbalizar necessidades Pode criar expectativas irreais de prazo
Brainstorming Geração livre de ideias em grupo, sem julgamento Fase inicial, levantamento amplo Pode gerar requisitos inviáveis
💡 JAD — Joint Application Design
Técnica de workshop facilitado onde usuários, analistas e desenvolvedores colaboram intensivamente para definir requisitos. Mais eficiente que entrevistas individuais sequenciais. O facilitador (analista neutro) guia a sessão; um escriba registra. Muito cobrada pela Cesgranrio pelo nome e propósito.

Histórias de Usuário

⭐ Formato Padrão
Como [tipo de usuário / persona],
Quero [objetivo / funcionalidade],
Para que [benefício / valor de negócio].

Exemplo: "Como analista financeiro da Petrobras, quero visualizar o custo de produção por plataforma em tempo real, para que possa identificar desvios orçamentários antes do fechamento mensal."

Critério INVEST

LetraCritérioO que significa
IIndependentIndependente de outras histórias — pode ser desenvolvida em qualquer ordem
NNegotiableNegociável — detalhes são discutidos entre PO e Dev Team, não são contratos rígidos
VValuableValiosa — entrega valor perceptível ao usuário ou negócio
EEstimableEstimável — o Dev Team consegue estimar o esforço de implementação
SSmallPequena — cabe em uma Sprint; se não couber, deve ser dividida (Epic → Histórias)
TTestableTestável — possui critérios de aceitação claros para verificar quando está "pronta"

Critérios de Aceitação

Condições específicas que devem ser satisfeitas para que a história seja considerada concluída. Escritos como cenários (Given/When/Then) ou lista de comportamentos esperados.

Formato Gherkin (BDD)
Dado que o analista está logado no sistema
E está na tela de relatórios de produção
Quando selecionar a plataforma P-76 e o período "Janeiro 2024"
Então o sistema deve exibir o custo total em menos de 3 segundos
E o valor deve corresponder ao registrado no ERP
E deve haver opção de exportar em PDF e Excel

Épicos, Features e Histórias

1

Épico

Grande iniciativa que não cabe em uma Sprint. Ex: "Módulo de Gestão de Produção". Deve ser dividido em features e histórias.

2

Feature

Funcionalidade significativa dentro do épico. Ex: "Dashboard de Custos por Plataforma". Pode ser dividida em histórias.

3

História de Usuário

Unidade de trabalho que cabe em uma Sprint. Ex: "Como analista, quero visualizar custo por plataforma..." Testável e entregável.

Gerenciamento de Requisitos

Rastreabilidade de Requisitos

Rastreabilidade é a capacidade de acompanhar a vida de um requisito — de onde veio, como foi implementado e onde foi testado.

DireçãoO que rastreia
Forward (para frente)Requisito → Design → Código → Teste — garante que tudo foi implementado
Backward (para trás)Teste → Código → Design → Requisito — garante que nada foi implementado sem requisito

Baseline de Requisitos

💡 O que é Baseline
Baseline é a versão aprovada e congelada do documento de requisitos em um determinado momento. Serve como referência para controle de mudanças. Qualquer alteração após a baseline deve passar pelo processo formal de controle de mudanças (change request, análise de impacto, aprovação). Evita o "scope creep" (expansão descontrolada do escopo).

Processo de Gerenciamento de Requisitos

1

Elicitação

Levantar requisitos junto aos stakeholders usando técnicas adequadas.

2

Análise

Classificar, priorizar, identificar conflitos e verificar completude e consistência.

3

Especificação

Documentar formalmente em ERS (Especificação de Requisitos de Software) ou backlog.

4

Validação

Confirmar com stakeholders que os requisitos documentados refletem as necessidades reais.

5

Gerenciamento de Mudanças

Controlar alterações via processo formal — análise de impacto, aprovação e rastreabilidade.
