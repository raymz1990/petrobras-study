SGBD — Sistemas de Gerenciamento de BD

Arquitetura de SGBDs, tipos (relacional, objeto-relacional, orientado a objetos), índices, otimização de consultas, controle de concorrência, recuperação de falhas e comparativo dos principais SGBDs do mercado.

Destaques Cesgranrio — SGBDs

  • Índice clustered: dados físicos ordenados pela chave. Non-clustered: estrutura separada com ponteiros
  • Apenas um índice clustered por tabela (os dados só podem estar em uma ordem física)
  • Índice bitmap: ideal para colunas de baixa cardinalidade (sexo, status, categoria)
  • Deadlock: duas transações esperando uma pela outra — SGBD detecta e aborta uma
  • Write-Ahead Log (WAL): log é gravado ANTES dos dados — garante durabilidade e recuperação
  • Arquitetura em 3 camadas: externa (visões), conceitual (esquema lógico), interna (física)

🏛️
Arquitetura de SGBDs

Arquitetura em 3 Níveis (ANSI/SPARC)

1

Nível Externo (Visões)

O que cada usuário ou aplicação enxerga. Múltiplas visões diferentes do mesmo banco para diferentes perfis de usuário. Abstrai a complexidade do esquema completo.

Exemplo: Analista financeiro vê apenas dados de custo. Operador vê apenas dados de produção.

2

Nível Conceitual (Esquema Lógico)

A visão completa e integrada do banco — estrutura lógica de todos os dados, relacionamentos e restrições. Independente de implementação física.

Exemplo: O modelo entidade-relacionamento, o schema de todas as tabelas.

3

Nível Interno (Físico)

Como os dados são fisicamente armazenados em disco. Estruturas de armazenamento, índices, particionamento, compressão.

Exemplo: B-trees para índices, heap files, tablespaces.

Independência de Dados

🧠
Independência Lógica
Mudanças no esquema conceitual (adicionar tabela, coluna) não afetam as visões externas dos usuários. A mais difícil de atingir.
💾
Independência Física
Mudanças no armazenamento físico (criar índice, mover para outro disco) não afetam o esquema conceitual. Mais fácil de atingir.

ComponenteFunção

Índices

⭐ O que é um Índice
Um índice é uma estrutura de dados auxiliar que acelera a recuperação de registros, ao custo de espaço adicional e overhead nas operações de escrita (INSERT, UPDATE, DELETE). É o principal recurso de otimização de queries.

Tipos de Índices

TipoComo funcionaQuando usarLimitações
Clustered (Agrupado) Os dados físicos na tabela são ordenados pela chave do índice. O índice É a tabela. PK, colunas usadas em ORDER BY e range queries frequentes Apenas 1 por tabela — os dados só podem estar em uma ordem física
Non-Clustered (Não agrupado) Estrutura separada com ponteiros para os registros reais. Pode ter vários. Colunas de busca frequente que não são a PK Lookup adicional — dois acessos: índice + dado
Bitmap Um bitmap (vetor de bits) por valor possível da coluna Colunas de BAIXA cardinalidade: sexo, status, categoria Ruim para colunas de alta cardinalidade (CPF, email)
Hash Função hash mapeia valor → posição no disco Apenas buscas por igualdade exata (= ) Não suporta range queries (<, >, BETWEEN)
B-TreeÁrvore balanceada — O(log n) para busca, inserção e deleçãoCaso geral — suporta igualdade e range queriesOverhead de manutenção em alta taxa de escrita
Cobrindo (Covering) Inclui todas as colunas necessárias para uma query — evita lookup na tabela Queries frequentes com poucas colunas específicas Ocupa mais espaço
⚠️ Índice Clustered — Apenas 1 por tabela
A banca frequentemente testa: "Quantos índices clustered pode ter uma tabela?" → Resposta: apenas 1. Pois os dados físicos só podem estar ordenados de uma forma. Em SQL Server, a PK cria automaticamente um clustered index. No MySQL (InnoDB), a PK sempre é o clustered index.

Quando índices PREJUDICAM a performance

✍️
Alta taxa de escrita
INSERT, UPDATE e DELETE precisam atualizar todos os índices da tabela — muitos índices = writes lentos.
🎲
Baixa seletividade
Índice em coluna com poucos valores distintos (sexo: M/F) em tabelas OLTP — o SGBD prefere full scan.
📦
Tabelas pequenas
Full table scan em tabelas pequenas é mais rápido que usar o índice — overhead do lookup supera o benefício.

Query Plan — Analisando a Execução

SQL — Analisando plano de execução
-- PostgreSQL / MySQL
EXPLAIN ANALYZE
SELECT nome, salario
FROM funcionarios
WHERE depto_id = 10
  AND salario > 5000;

-- Saída indica se usou Index Scan ou Seq Scan
-- Index Scan: usou índice (bom para queries seletivas)
-- Sequential Scan: leu a tabela inteira (bom para baixa seletividade)
-- Nested Loop / Hash Join / Merge Join: tipo de JOIN usado

Controle de Concorrência

SGBDs modernos permitem múltiplas transações simultâneas. O controle de concorrência garante que essas transações se comportem corretamente (isolamento do ACID).

Problemas de Concorrência

ProblemaDescriçãoExemplo
Dirty Read T1 lê dados escritos por T2 que ainda não fez COMMIT T2 atualiza salário para 10k. T1 lê 10k. T2 faz ROLLBACK. T1 usou dado inexistente.
Non-Repeatable Read T1 lê o mesmo dado duas vezes e obtém valores diferentes (T2 alterou e fez COMMIT entre as leituras) T1 lê saldo=1000. T2 debita 200 e commita. T1 lê saldo=800. Valores diferentes na mesma transação.
Phantom Read T1 executa a mesma query duas vezes e obtém conjuntos de linhas diferentes (T2 inseriu/deletou linhas entre as execuções) T1 conta funcionários (N=50). T2 insere 5. T1 reconta (N=55). "Linhas fantasma" apareceram.
Lost Update Duas transações leem o mesmo valor, modificam e salvam — a segunda sobrescreve a primeira T1 e T2 leem saldo=1000. T1 soma 200 e salva 1200. T2 soma 100 e salva 1100. Os +200 de T1 são perdidos.

Técnicas de Controle

🔐
Locking (Bloqueios)
Shared Lock (S): para leitura — múltiplos simultâneos. Exclusive Lock (X): para escrita — apenas um, bloqueia todos os outros.
📷
MVCC
Multi-Version Concurrency Control: cada transação vê um snapshot do banco no momento do início. Readers não bloqueiam writers. Usado por PostgreSQL, Oracle, MySQL InnoDB.
🎯
Optimistic Locking
Assume que conflitos são raros. Não bloqueia na leitura — verifica conflito apenas no commit. Ideal para workloads com muita leitura e pouca escrita.

Deadlock

⚠️ Deadlock — Impasse entre Transações
Deadlock ocorre quando T1 espera por um recurso bloqueado por T2, e T2 espera por um recurso bloqueado por T1 — ciclo de espera eterno.

Detecção: O SGBD periodicamente verifica ciclos no grafo de espera (wait-for graph).
Resolução: O SGBD escolhe uma vítima (geralmente a transação mais nova ou a com menor custo) e a aborta — a outra pode prosseguir.
Prevenção: Adquirir locks sempre na mesma ordem; usar timeouts.

Recuperação de Falhas

Write-Ahead Log (WAL)

⭐ WAL — O Princípio Fundamental
Toda modificação deve ser registrada no LOG antes de ser aplicada nos dados em disco. O log é persistido antes dos dados ("write-ahead" = escreve antes).

Isso garante que, em caso de falha, o SGBD pode:
• REDO: reaplicar operações de transações que fizeram COMMIT mas não foram para o disco
• UNDO: desfazer operações de transações que não fizeram COMMIT (deixar banco consistente)

Tipos de Falha e Recuperação

Tipo de FalhaO que ocorreRecuperação
Falha de Transação Erro lógico (divisão por zero, violação de constraint) ou deadlock ROLLBACK automático — UNDO das operações da transação
Falha do Sistema Queda de energia, crash do SO — memória (buffer) é perdida, disco preservado Usar WAL: REDO transações commitadas, UNDO transações em aberto
Falha de Mídia Falha física do disco — dados permanentes perdidos Restaurar backup + reaplicar log (archive log) até o ponto de falha

Checkpoint

💡 Checkpoint
O SGBD periodicamente força a escrita de todas as páginas sujas (dirty pages) do buffer para o disco e registra um checkpoint no log. Em caso de falha, a recuperação começa a partir do último checkpoint — não precisa reler todo o log desde o início, acelerando a recuperação.

A Petrobras utiliza uma combinação de SGBDs para diferentes necessidades:
• Oracle / SQL Server: sistemas ERP e transacionais críticos
• PostgreSQL: aplicações internas e projetos de modernização
• Redshift / BigQuery: Data Warehouse analítico em cloud
• Hadoop/Spark + Data Lake: processamento de dados sísmicos e IoT de plataformas
• Redis: cache para dashboards operacionais de alta demanda

Critérios de Seleção de SGBD

💰
Custo Total
Licença, infraestrutura, suporte, treinamento. Open source nem sempre é mais barato (TCO).
📈
Escalabilidade
Vertical (mais hardware) vs horizontal (mais servidores). NoSQL geralmente escala melhor horizontalmente.
⚛️
Consistência
ACID completo (relacional) vs eventual consistency (NoSQL). Aplicações financeiras exigem ACID.
🔧
Expertise disponível
Profissionais qualificados no mercado. Oracle e PostgreSQL têm ampla base de profissionais.
