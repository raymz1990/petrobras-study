Tipos de Bancos NoSQL

NoSQL ("Not Only SQL") é o termo para bancos de dados que adotam modelos de dados diferentes do relacional. Cada tipo é otimizado para um padrão específico de acesso e estrutura de dados.

Os 4 Tipos Principais

📄 Banco de Documentos — MongoDB, CouchDB, Firestore

Armazena dados como documentos JSON/BSON com schema flexível — cada documento pode ter campos diferentes.

JSON Document
{
  "_id": "prod_001",
  "nome": "Válvula Subsea X7",
  "categoria": "Equipamentos",
  "especificacoes": {
    "pressao_max": "3500 psi",
    "material": "Inox 316L",
    "certificacoes": ["API 6D", "ISO 14313"]
  },
  "estoque_por_plataforma": {
    "P-75": 12,
    "P-76": 8
  }
}

✅ Ideal para: catálogos de produtos com atributos variáveis, perfis de usuário, conteúdo CMS, documentos semi-estruturados.

❌ Evitar quando: dados altamente relacionais com muitos JOINs necessários.

🔑 Banco Chave-Valor — Redis, DynamoDB, Riak

Estrutura mais simples: cada item é um par chave → valor. Extremamente rápido para operações de leitura/escrita por chave.

Redis — Exemplos
SET sessao:user_42 '{"nome":"Ana","depto":"TI","exp":3600}'
GET sessao:user_42

SET cache:relatorio_producao_jan24 "{dados...}" EX 3600   # expira em 1h
INCR contador:visitas_homepage   # contador atômico

✅ Ideal para: cache de sessão, filas de mensagens, contadores, leaderboards, dados temporários de alta velocidade.

❌ Evitar quando: necessidade de consultas complexas ou filtros por campos internos do valor.

📊 Banco Colunar — Apache Cassandra, HBase, Redshift

Armazena dados por coluna em vez de por linha. Cada família de colunas agrupa colunas relacionadas. Otimizado para escrita massiva e leitura de colunas específicas.

Cassandra CQL
CREATE TABLE leituras_sensor (
    sensor_id   UUID,
    timestamp   TIMESTAMP,
    temperatura FLOAT,
    pressao     FLOAT,
    PRIMARY KEY (sensor_id, timestamp)  -- partition key + clustering key
) WITH CLUSTERING ORDER BY (timestamp DESC);

✅ Ideal para: séries temporais (IoT, logs), dados de telemetria, analytics em larga escala, alta taxa de escrita distribuída.

❌ Evitar quando: consultas ad-hoc complexas, relacionamentos entre entidades.

🕸️ Banco de Grafos — Neo4j, Amazon Neptune, JanusGraph

Armazena dados como nós (vértices) e arestas (relacionamentos) com propriedades. Otimizado para percorrer relacionamentos complexos.

Cypher (Neo4j)
-- Criar nós e relacionamentos
CREATE (ana:Pessoa {nome: "Ana"})-[:TRABALHA_COM]->(carlos:Pessoa {nome: "Carlos"})
CREATE (carlos)-[:GERENCIA]->(projeto:Projeto {nome: "Pipeline ETL"})

-- Consultar: amigos de amigos de Ana
MATCH (ana:Pessoa {nome:"Ana"})-[:TRABALHA_COM*2]->(pessoa)
RETURN pessoa.nome

✅ Ideal para: redes sociais, sistemas de recomendação, detecção de fraude, rotas e mapas, redes de conhecimento.

❌ Evitar quando: dados simples sem relacionamentos complexos — overhead desnecessário.

Banco em Memória

💡 In-Memory Database
Armazenam dados primariamente na RAM, não em disco. Velocidade de acesso ordens de magnitude maior que bancos tradicionais (microssegundos vs milissegundos).

Redis: chave-valor em memória + persistência opcional (RDB snapshots, AOF logs).
Casos de uso Petrobras: cache de dashboards operacionais, filas de mensagens para sistemas SCADA, contadores de acesso.

Teorema CAP

⭐ Teorema de Brewer (CAP)
Em um sistema distribuído, é impossível garantir simultaneamente mais de dois dos seguintes três atributos:
Consistency (Consistência) — todos os nós veem os mesmos dados ao mesmo tempo
Availability (Disponibilidade) — toda requisição recebe uma resposta (não necessariamente atual)
Partition Tolerance (Tolerância a Partição) — o sistema opera mesmo com falhas de comunicação entre nós

Classificação dos Bancos pelo CAP

TipoGaranteExemplosTrade-off
CPConsistência + Tolerância a PartiçãoHBase, MongoDB (config), Redis (modo cluster)Pode ficar indisponível sob partição
APDisponibilidade + Tolerância a PartiçãoCassandra, CouchDB, DynamoDBDados podem ser temporariamente inconsistentes
CAConsistência + DisponibilidadeSGBDs relacionais tradicionais (single node)Não tolera partição de rede — não escala horizontalmente
💡 Na prática — BASE vs ACID
Bancos NoSQL frequentemente adotam o modelo BASE (em contraposição ao ACID):
BAsically Available — disponibilidade básica sempre
Soft state — o estado pode mudar ao longo do tempo mesmo sem input
Eventually consistent — os dados eventualmente ficarão consistentes em todos os nós

Big Data — Os 5 Vs

📦
Volume
Quantidade massiva de dados — terabytes a petabytes. A Petrobras gera dados de sensores, imagens sísmicas e registros operacionais em escala gigantesca.
⚡
Velocidade
Alta taxa de geração e necessidade de processamento rápido (streaming). Dados de sensores IoT gerados em tempo real requerem processamento contínuo.
🎲
Variedade
Dados em múltiplos formatos: estruturados (SQL), semi-estruturados (JSON, XML), não-estruturados (imagens sísmicas, vídeos, textos livres).
✅
Veracidade
Qualidade e confiabilidade dos dados. Dados imprecisos ou incompletos levam a decisões erradas. Inclui limpeza, validação e governança de dados.
💡
Valor
O dado precisa gerar valor para o negócio. Big Data sem valor é apenas ruído caro. O objetivo final é transformar volume em insights acionáveis.
⚠️ O 5º V é VALOR, não Verificabilidade!
A banca pode apresentar "Verificabilidade" como um dos Vs — isso está ERRADO. Os 5 Vs reconhecidos são: Volume, Velocidade, Variedade, Veracidade e Valor. Memorize: V-V-V-V-V → Vol-Vel-Var-Ver-Val.

Data Lake e Soluções para Big Data

⭐ Data Lake — Definição
Repositório centralizado que permite armazenar todos os dados estruturados e não-estruturados em qualquer escala, no formato original, sem necessidade de definir schema previamente (schema on read).

Data Lake vs Data Warehouse

AspectoData LakeData Warehouse
SchemaSchema on Read — definido na consultaSchema on Write — definido na carga
DadosBrutos, qualquer formatoProcessados, estruturados
CustoBaixo (object storage)Alto (infra especializada)
UsuáriosData Scientists, EngenheirosAnalistas de negócio, gestores
QualidadeRaw — pode virar "Data Swamp"Alta qualidade e governança
PerformanceVariável (depende da query)Otimizada para analytics
ExemplosS3, Azure Data Lake, GCSRedshift, BigQuery, Snowflake
⚠️ Data Swamp
Um Data Lake sem governança, catalogação e qualidade de dados torna-se um Data Swamp (pântano de dados) — dados existem mas ninguém sabe o que são, onde estão ou se são confiáveis. Governança e metadados são essenciais.

Lakehouse — Arquitetura Moderna

Arquitetura que combina flexibilidade do Data Lake com as capacidades analíticas e de governança do Data Warehouse. Tecnologias: Delta Lake (Databricks), Apache Iceberg, Apache Hudi.

Qualidade de Dados e MDM

✅
Completude
Todos os campos obrigatórios estão preenchidos? Sem NULLs indesejados.
🎯
Acurácia
Os dados refletem a realidade? Valores corretos e não corrompidos.
🔄
Consistência
O mesmo dado tem o mesmo valor em diferentes sistemas? Sem duplicatas conflitantes.
⏱️
Atualidade
Os dados estão atualizados? Latência aceitável para o caso de uso.
💡 MDM — Master Data Management
Gestão de dados mestres garante que entidades-chave do negócio (clientes, produtos, fornecedores, localidades) tenham uma versão "dourada" consistente em todos os sistemas. Evita que o mesmo cliente apareça como "Petrobras S.A.", "PETROBRAS" e "Petróleo Brasileiro S.A." em sistemas diferentes.
