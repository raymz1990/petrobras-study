ETL & Integração de Dados

ETL (Extract, Transform, Load), ELT, transferência de arquivos, integração via base de dados e padrões de integração entre sistemas. Fundação do ecossistema de dados analíticos.

⏱ ~40 min
🎯 Média incidência
👑

Destaques Cesgranrio — ETL

  • ETL transforma ANTES de carregar; ELT carrega bruto e transforma no destino
  • Área de staging: zona temporária entre fonte e destino no ETL
  • ELT é favorecido em ambientes cloud com grande capacidade computacional
  • Diferença entre integração batch (programada) e real-time (evento/streaming)
  • CDC (Change Data Capture): captura apenas as mudanças, não a tabela inteira

🔄
ETL vs ELT

ETL — Extract, Transform, Load (tradicional)

E

Extract — Extração

Coleta dados das fontes originais: bancos relacionais, arquivos CSV/XML/JSON, APIs, sistemas legados, ERPs. Os dados são extraídos sem transformação e colocados em uma área de staging.

T

Transform — Transformação

Limpeza, padronização, enriquecimento e agregação dos dados na área de staging antes de carregar no destino. Inclui: conversão de tipos, remoção de duplicatas, aplicação de regras de negócio, joins entre fontes.

L

Load — Carga

Carrega os dados transformados no destino final (Data Warehouse, Data Mart). Pode ser carga completa (full load) ou incremental (apenas mudanças).

ELT — Extract, Load, Transform (moderno)

E

Extract — Extração

Idêntico ao ETL — coleta dados das fontes originais.

L

Load — Carga (ANTES da transformação)

Dados são carregados brutos diretamente no destino (Data Lake ou DW cloud com alto poder computacional).

T

Transform — Transformação no destino

A transformação ocorre dentro do destino, usando o poder computacional do DW cloud (BigQuery, Redshift, Snowflake). Ferramenta popular: dbt (data build tool).

⭐ Área de Staging
No ETL, a área de staging é uma zona temporária onde os dados extraídos são depositados antes da transformação. Funciona como "buffer" entre as fontes e o DW. Permite reprocessamento em caso de erro sem reextrair das fontes. Pode ser um banco de dados separado, schema específico ou diretório de arquivos.

Transformação — Operações Comuns

🧹
Limpeza
Remover duplicatas, corrigir erros tipográficos, tratar NULLs, padronizar formatos de data e telefone.
🔄
Padronização
Unificar códigos e categorias entre sistemas (ex: "M/F" → "Masculino/Feminino").
🔗
Enriquecimento
Combinar dados de múltiplas fontes para adicionar contexto (ex: adicionar dados geográficos via CEP).
📊
Agregação
Sumarizar dados (ex: vendas diárias → vendas mensais) para tabelas de fato pré-agregadas.
🔑
Surrogate Keys
Gerar chaves substitutas artificiais para as dimensões, independentes das chaves das fontes.
📅
SCD
Slowly Changing Dimensions — tratar mudanças históricas nas dimensões (ex: funcionário mudou de departamento).

SCD — Slowly Changing Dimensions

TipoComportamentoHistórico?
Tipo 1Sobrescreve o valor antigo — sem histórico❌
Tipo 2Cria novo registro com datas de vigência — preserva histórico completo✅ Completo
Tipo 3Adiciona coluna "valor anterior" — histórico limitado (só 1 mudança)⚠️ Parcial
💡 SCD Tipo 2 — O mais cobrado
Adiciona colunas: data_inicio, data_fim, is_current. Quando o funcionário muda de departamento, o registro atual recebe data_fim e is_current=FALSE, e um novo registro é criado com o novo departamento e is_current=TRUE. Permite análise histórica de "qual era o departamento do funcionário em 2022?"

Padrões de Integração de Dados

Transferência de Arquivos

Forma mais simples de integração. Um sistema gera um arquivo (CSV, XML, JSON, XLSX) e outro sistema o consome. Comunicação assíncrona e desacoplada.

Protocolo/MecanismoUso típico
SFTP/FTPTransferência segura de arquivos entre sistemas on-premises
S3/Object StorageStaging em cloud — sistema deposita arquivo, outro consome
Email/anexoRelatórios e dados para usuários finais (baixa automação)
EDIElectronic Data Interchange — padrão B2B para NF, pedidos

Integração via Base de Dados

Um sistema lê diretamente do banco de dados de outro sistema ou de um banco de dados intermediário (banco de integração).

⚠️ Problema do acoplamento direto
Integração via acesso direto ao banco do sistema A pelo sistema B cria forte acoplamento — qualquer mudança no schema do banco A quebra o sistema B. Solução: usar views, APIs ou banco de integração intermediário.

Integração via API (REST/SOAP)

🔌
REST API
Padrão moderno. Usa HTTP (GET/POST/PUT/DELETE), JSON. Stateless. Amplamente adotado em microserviços.
📜
SOAP
Protocolo mais antigo. Usa XML e WSDL. Ainda presente em sistemas legados e integrações bancárias.
📨
Mensageria
Message Broker (RabbitMQ, Kafka, SQS). Desacopla produtores e consumidores. Resiliente a falhas.
🔔
Webhooks
Sistema A notifica sistema B via HTTP POST quando evento ocorre. Integração event-driven em tempo real.
