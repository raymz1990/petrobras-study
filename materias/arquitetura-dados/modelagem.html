Níveis de Modelagem

1

Modelo Conceitual — O QUÊ existe

Representação de alto nível, independente de tecnologia. Foco nas entidades do negócio e seus relacionamentos. Usa DER (Diagrama Entidade-Relacionamento).

Elementos: Entidades, Atributos, Relacionamentos, Cardinalidade.

Ferramentas: brModelo, Lucidchart, draw.io.

2

Modelo Lógico — COMO está organizado

Traduz o conceitual para estruturas relacionais (tabelas, colunas, chaves), ainda independente do SGBD específico. Define tipos genéricos e constraints.

Elementos: Tabelas, Colunas, PK, FK, Índices lógicos.

3

Modelo Físico — ONDE e COMO implementar

Específico para um SGBD (Oracle, PostgreSQL, MySQL). Define tipos de dados precisos, particionamento, tablespaces, índices físicos e otimizações de performance.

Elementos: CREATE TABLE com tipos específicos, índices, partições, clusters.

Engenharia Reversa

💡 Engenharia Reversa de Dados
Processo de gerar um modelo de dados (conceitual ou lógico) a partir de um banco de dados existente. Útil para documentar sistemas legados sem documentação, migrar entre SGBDs ou refatorar esquemas. Ferramentas: MySQL Workbench, DBeaver, Oracle SQL Developer.

Metadados

Metadados são "dados sobre dados" — descrevem a estrutura, o conteúdo e o contexto dos dados. Ex: nome da tabela, tipo de coluna, constraint aplicada, última atualização, dono do objeto.

No contexto de DW, o catálogo de metadados documenta fontes, transformações ETL, significado de cada campo e regras de negócio.

Modelo Relacional

Conceitos Fundamentais

📋
Relação (Tabela)
Conjunto de tuplas com o mesmo esquema. Sem linhas duplicadas, sem ordenação definida.
➡️
Tupla (Linha)
Um registro da relação. Cada tupla é única — garantida pela chave primária.
⬇️
Atributo (Coluna)
Propriedade de uma entidade. Domínio define os valores permitidos.
🔑
Chave Primária (PK)
Identifica uniquamente cada tupla. Não aceita NULL nem duplicatas.
🔗
Chave Estrangeira (FK)
Referencia PK de outra tabela. Garante integridade referencial.
🎯
Chave Candidata
Atributo(s) que poderia(m) ser PK — único e não-nulo. A PK é escolhida entre as candidatas.

Cardinalidade dos Relacionamentos

CardinalidadeExemploImplementação
1:1Funcionário ↔ Cartão de PontoFK em qualquer lado (geralmente no lado "mais fraco")
1:NDepartamento → FuncionáriosFK no lado N (funcionario.depto_id referencia departamento.id)
N:MFuncionários ↔ ProjetosTabela associativa com as duas FKs (funcionario_projeto)
SQL — Implementando N:M
-- Tabela associativa para N:M
CREATE TABLE funcionario_projeto (
    funcionario_id INT REFERENCES funcionarios(id),
    projeto_id     INT REFERENCES projetos(id),
    papel          VARCHAR(50),
    horas_semana   INT,
    PRIMARY KEY (funcionario_id, projeto_id)  -- PK composta
);

Integridade Referencial

Garante que uma FK sempre aponte para um registro existente na tabela referenciada (ou seja NULL). Violações ocorrem ao:

  • Inserir um registro filho com FK inexistente na tabela pai
  • Deletar um registro pai que ainda tem filhos (sem CASCADE)
  • Atualizar a PK do pai para um valor diferente (sem CASCADE)

Normalização

Normalização é o processo de organizar atributos e tabelas para minimizar redundância e dependências problemáticas. Cada Forma Normal (FN) adiciona restrições sobre a anterior.

⭐ Progressão das Formas Normais
1FN → 2FN → 3FN → BCNF → 4FN → 5FN
Cada nível pressupõe que o anterior foi satisfeito.
Para a Cesgranrio: domine 1FN, 2FN, 3FN e BCNF.

1FN — Primeira Forma Normal

Regra
Todos os atributos devem ser atômicos (indivisíveis) e monovalorados. Sem grupos repetidos, sem atributos multivalorados, sem listas em células.
❌ Viola 1FN✅ Satisfaz 1FN
telefones = "11-9999, 11-8888" (lista)Tabela separada: funcionario_telefone(func_id, telefone)
endereco = "Rua X, 100, SP" (composto)rua, numero, cidade como colunas separadas

2FN — Segunda Forma Normal

Regra
Deve estar em 1FN + todo atributo não-chave deve depender da chave primária completa (sem dependências parciais). Relevante apenas quando há chave primária composta.
Exemplo de violação 2FN
-- PK composta: (pedido_id, produto_id)
Pedido_Produto(pedido_id, produto_id, quantidade, nome_produto)
--                                                ↑
-- nome_produto depende apenas de produto_id (dependência PARCIAL)
-- Viola 2FN!

-- Solução: separar em duas tabelas
Pedido_Produto(pedido_id, produto_id, quantidade)  -- depende da PK completa
Produto(produto_id, nome_produto)                  -- nome depende só de produto_id

3FN — Terceira Forma Normal

Regra
Deve estar em 2FN + nenhum atributo não-chave deve depender de outro atributo não-chave (sem dependências transitivas).
Exemplo de violação 3FN
-- PK: func_id
Funcionario(func_id, nome, depto_id, depto_nome)
--                                   ↑
-- depto_nome depende de depto_id (não-chave) → transitiva
-- func_id → depto_id → depto_nome (transitiva!)
-- Viola 3FN!

-- Solução:
Funcionario(func_id, nome, depto_id)
Departamento(depto_id, depto_nome)

BCNF — Boyce-Codd Normal Form

Regra
Para toda dependência funcional X → Y, X deve ser uma superchave. BCNF é mais restritiva que 3FN — trata casos de múltiplas chaves candidatas sobrepostas.
⚠️ 3FN vs BCNF — Pegadinha
Toda relação em BCNF está em 3FN. Mas uma relação pode estar em 3FN sem estar em BCNF. A diferença ocorre quando há múltiplas chaves candidatas que se sobrepõem em atributos. Para a maioria dos casos práticos, 3FN e BCNF são equivalentes.

Modelagem Dimensional

Usada em Data Warehouses e sistemas analíticos (OLAP). Otimizada para consultas analíticas, não para transações. Desnormalizada para performance de leitura.

ConteúdoMétricas numéricas (o QUÊ medir)Atributos descritivos (contexto de análise)
Exemplosvalor_venda, qtd_itens, custonome_produto, cidade, data, nome_cliente
CardinalidadeMuitas linhas (granular)Poucas linhas (relativamente)

NormalizaçãoDesnormalizadaDesnormalizada (estrela) ou normalizada (floco)

Star Schema vs Snowflake

Star Schema — Estrutura
-- Tabela FATO no centro
fato_vendas:
  venda_id    (PK/surrogate)
  data_id     (FK → dim_tempo)
  produto_id  (FK → dim_produto)
  cliente_id  (FK → dim_cliente)
  loja_id     (FK → dim_loja)
  valor_venda  ← MÉTRICA
  quantidade   ← MÉTRICA
  desconto     ← MÉTRICA

-- Dimensões desnormalizadas (todas as infos em UMA tabela)
dim_produto:
  produto_id, nome, categoria, subcategoria, marca, fornecedor

-- Snowflake: dim_produto seria normalizada
dim_produto:   produto_id, nome, subcategoria_id
dim_subcateg:  subcateg_id, nome, categoria_id
dim_categoria: categoria_id, nome
⭐ Star vs Snowflake — Decisão
Star Schema: dimensões desnormalizadas → menos JOINs → queries mais rápidas → mais espaço.
Snowflake: dimensões normalizadas → mais JOINs → queries mais lentas → menos espaço.
Para DW: geralmente preferido o Star (performance analítica > economia de espaço).
