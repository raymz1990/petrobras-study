Fundamentos do Modelo Relacional

⭐ Modelo Relacional — Edgar F. Codd (1970)
Proposto por Codd na IBM, o modelo relacional organiza dados em relações (tabelas) com linhas (tuplas) e colunas (atributos). É baseado na teoria matemática de conjuntos e lógica de predicados de primeira ordem.

Hierarquia de Chaves

SK

Superchave

Qualquer conjunto de atributos que identifica uniquamente cada tupla. Pode ter atributos "extras" desnecessários. Ex: {CPF}, {CPF, Nome}, {CPF, Nome, Email} — todos são superchaves se CPF é único.

CK

Chave Candidata

Superchave MÍNIMA — remove qualquer atributo e deixa de ser superchave. Ex: {CPF} e {Email} podem ambos ser chaves candidatas. A relação pode ter múltiplas chaves candidatas.

PK

Chave Primária (Primary Key)

A chave candidata escolhida pelo projetista para identificar as tuplas. Uma e apenas UMA por relação. Nunca aceita NULL. As demais candidatas viram UNIQUE.

FK

Chave Estrangeira (Foreign Key)

Atributo(s) em uma relação que referenciam a PK de outra relação. Garante integridade referencial. Pode ser NULL (indica ausência de relacionamento).

Propriedades de uma Relação

🔢
Sem Duplicatas
Não pode haver duas tuplas idênticas em todos os atributos — garantido pela PK.
🔀
Sem Ordenação
Tuplas e atributos não têm ordem definida — qualquer query pode retornar em qualquer ordem.
⚛️
Atributos Atômicos
Cada valor é indivisível (1FN) — sem listas, sem grupos repetidos.
📋
Valores de Domínio
Cada valor deve pertencer ao domínio definido para o atributo.

🧮
Álgebra Relacional

A álgebra relacional define operações sobre relações que retornam novas relações. É a base teórica das queries SQL.

Operações Fundamentais

OperaçãoSímboloO que fazEquivalente SQL
Seleção σcondição(R) Filtra LINHAS que satisfazem a condição WHERE
Projeção πatributos(R) Filtra COLUNAS — seleciona atributos específicos SELECT colunas
União R ∪ S Todas as tuplas de R e S (sem duplicatas) UNION
Interseção R ∩ S Tuplas que aparecem em AMBOS R e S INTERSECT
Diferença R − S Tuplas em R que NÃO estão em S EXCEPT / MINUS
Produto Cartesiano R × S Todas as combinações de tuplas de R e S CROSS JOIN
Junção Natural R ⋈ S Combina tuplas com valores iguais nos atributos comuns NATURAL JOIN / INNER JOIN
Renomeação ρnovo(R) Renomeia a relação ou atributos AS (alias)
⭐ Seleção vs Projeção — A Distinção Mais Cobrada
σ (Seleção): filtra LINHAS (tuplas) com base em condição. Como o WHERE do SQL.
"σdepto='TI'(Funcionarios)" = todas as linhas onde o departamento é TI

π (Projeção): filtra COLUNAS (atributos). Como o SELECT de colunas específicas.
"πnome, salario(Funcionarios)" = apenas as colunas nome e salário de todos os funcionários
Álgebra relacional → SQL
-- Álgebra: σ_{depto='TI'}(π_{nome, salario}(Funcionarios))
-- SQL equivalente:
SELECT nome, salario
FROM Funcionarios
WHERE depto = 'TI';

-- Álgebra: π_{nome}(Funcionarios) − π_{nome}(Gerentes)
-- SQL equivalente:
SELECT nome FROM Funcionarios
EXCEPT
SELECT nome FROM Gerentes;

🛡️
Restrições de Integridade

Tipos de Restrições

🏛️
Integridade de Domínio
Todo valor deve pertencer ao domínio do atributo. Ex: salário deve ser numérico e positivo. Garantido por CHECK e tipos de dados.
🔑
Integridade de Entidade
A chave primária nunca pode ser NULL. Toda tupla deve ser identificável. Garantido por PRIMARY KEY.
🔗
Integridade Referencial
FK deve referenciar PK existente na tabela pai, ou ser NULL. Sem "chaves estrangeiras soltas". Garantido por FOREIGN KEY.
📋
Integridade de Usuário
Regras de negócio específicas definidas via CHECK, triggers e procedures. Ex: data_fim > data_inicio.

Integridade Referencial — Ações Referenciais

AçãoAo deletar o paiAo atualizar a PK do pai
RESTRICT / NO ACTIONBloqueia se houver filhos (padrão)Bloqueia se houver filhos

SET NULLFK dos filhos vira NULLFK dos filhos vira NULL

SQL — Definindo ações referenciais
CREATE TABLE funcionarios (
  id       INT PRIMARY KEY,
  nome     VARCHAR(100) NOT NULL,
  depto_id INT,
  CONSTRAINT fk_depto
    FOREIGN KEY (depto_id)
    REFERENCES departamentos(id)
    ON DELETE SET NULL     -- se depto for deletado, depto_id vira NULL
    ON UPDATE CASCADE      -- se depto.id mudar, funcionarios.depto_id atualiza
);

Transações e Propriedades ACID

⭐ O que é uma Transação
Uma transação é uma unidade lógica de trabalho composta por uma ou mais operações de banco de dados que devem ser executadas de forma completa ou nenhuma delas deve ser executada. Comanda com COMMIT (efetivar) ou ROLLBACK (desfazer).

Propriedades ACID

A

Atomicidade (Atomicity)

Tudo ou nada — a transação é executada completamente ou não é executada. Se qualquer parte falhar, todas as operações são desfeitas (ROLLBACK automático).

Exemplo: Transferência bancária: débito na conta A + crédito na conta B. Se o crédito falhar, o débito é desfeito.

C

Consistência (Consistency)

A transação leva o banco de um estado válido para outro estado válido. Todas as regras de integridade (constraints, triggers, etc.) devem ser respeitadas antes e depois.

I

Isolamento (Isolation)

Transações concorrentes não interferem entre si. Uma transação não vê os dados intermediários de outra em andamento. Controlado pelo nível de isolamento (READ COMMITTED, SERIALIZABLE, etc.).

D

Durabilidade (Durability)

Após COMMIT, os dados são permanentes mesmo em caso de falha de sistema (queda de energia, crash). Garantido por write-ahead logging (WAL) e recuperação de falha.

Dependências Funcionais

💡 Definição de Dependência Funcional
Dizemos que X → Y (X determina funcionalmente Y) quando, para qualquer dois tuplas de uma relação com o mesmo valor de X, elas também têm o mesmo valor de Y.

Exemplo: CPF → Nome (dado um CPF, sempre há um único nome associado)

Tipos de Dependências Funcionais

TipoDefiniçãoExemplo
Trivial Y é subconjunto de X. Sempre verdadeira. {CPF, Nome} → {Nome} — trivial, pois Nome ⊆ {CPF, Nome}
Não-Trivial Y não é subconjunto de X. CPF → Salário — não-trivial e útil
Parcial X é chave composta e Y depende de parte de X, não de X inteiro. (Pedido_ID, Produto_ID) → Nome_Produto — Nome depende só de Produto_ID (viola 2FN)
Total Y depende de todos os atributos de X (chave completa). (Pedido_ID, Produto_ID) → Quantidade — depende dos dois (correto para 2FN)
Transitiva X → Y e Y → Z (sendo Y não-chave), logo X → Z por transitividade. CPF → Depto_ID → Depto_Nome (viola 3FN)

Axiomas de Armstrong

Conjunto de regras de inferência completo e correto para derivar dependências funcionais:

AxiomaRegra
ReflexividadeSe Y ⊆ X, então X → Y (trivial)
AumentoSe X → Y, então XZ → YZ (adicionar mesmos atributos dos dois lados)
TransitividadeSe X → Y e Y → Z, então X → Z
UniãoSe X → Y e X → Z, então X → YZ
DecomposiçãoSe X → YZ, então X → Y e X → Z
PseudotransitividadeSe X → Y e WY → Z, então WX → Z
